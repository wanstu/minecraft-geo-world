# GeoWorld：仿原版花岗岩/安山岩矿团与入海口复核（2026-10-13）

## 用户需求

- 不是旧版仅露出一两格的薄矿纹，而是类似原版花岗岩、安山岩、闪长岩的**三维不规则矿团**。
- 按稀有度区分矿团大小及出现概率，但每一类均不能小到不具备“矿脉”的形状。
- 山区露头必须是地下三维矿体的一部分，不可单独贴在地表一层。
- 保留全部原版主世界矿物、群系及矿石变体；不注册新方块、生物、实体或玩法。模组删除后原版生存机制正常；原 GeoWorld 地形切换可能形成区块断层。
- 同期未完的问题：X≈-5890 Z≈4659 一处河口肉眼看起来不入海。不能因模型上接触而简单认定视觉问题已经解决。

## 矿脉算法调整

- 旧实现：长度约26～40格、截面半径约2～3格的细长椭球串，导致只有狭小可见条带。
- 新实现：参考原版岩石团的逻辑，以**较短弯曲中心线+数个变半径、彼此重叠的椭球**形成三维有厚度、不规则边界的矿体；多重椭球连成**单块矿团**，不生成孤立点状矿石。
- 几何长度与半径按矿物分组；稀有矿物通过现有生成权重和高度/地貌适配控制**出现次数**，而非缩减到两三块。煤铁铜最大；金/青金石/红石中等；钻石/绿宝石最小但始终具备地下厚度。
- 独立 `verifyGeoWorldMineralBodies`：每种矿物对3组随机种子及普通/高山矿团验证最小体积、三维尺寸、最大纵横比例和六邻接连通性（连通体≥96%）；通过后纳入常规 Gradle `check`。
- 代表样例去重后**矿团计划体积**（不代表实际可开采的矿石数量）：煤431~492、铁403~443、铜420~479、金/青金石207~223、红石233~244、钻石/绿宝石112~119。实际受到深度、岩石类别、宿主阻挡、不同矿团重叠影响；不是声明Minecraft每一矿脉固定数量。
- 高山露头：露头矿团中心略靠近真实裸岩，垂直椭球方向适度延伸；岩石覆盖验证仍保证土/草/雪/河床等非裸露STONE表面不能被随意矿化。裸岩山区 Seed -563659577384754347 的覆盖专项结果：800个不同可见矿点、最大六向连接可见矿片89格、露头向下最深10格、>=4层厚矿体列726；跨区块规划一致。
- 地下重复椭球覆盖位置先按chunk唯一bitset去重，再检查真实stone/deepslate宿主，不修改原矿物/花岗岩/安山岩方块的内容或属性。

## 海口过渡（仍需实机）

- 之前核查的 `saves/t1` 模型本身River/Ocean相邻，真实方块亦有水体接触，但河口只有约8格且两侧沙堤呈堤坝状。解决视觉/地貌问题不能凭接触点就说“已修复”。
- 在Go Waterbed标记 `OceanMouth` 最后出海段，只有出海的末端渐进扩大河槽半宽（普通半宽6时出海口上限15），不改变上游普通河流、原版水资源；Java Runtime读取该标识并与Go使用相同渐变、索引半径和实际河宽数据。
- `TestOceanMouthFlaresOnlyOnFinalReach` 验证上游不被误拓宽，口门渐进扩张，半宽上限正确。
- 因Go模型变化，Golden fixture(JSON+GEOWORLD)已经按故意改动重新生成；Go全量测试通过；Java的实际生成桥接测试通过。
- 仍需要**新世界/新生成区块**进行可视验证：不能因单元测试通过就宣布截图河口看起来已与海洋自然合流。

## 安全边界与验证

- 主世界8类矿物、16类STONE/DEEPSLATE矿石变体 + 紫水晶晶洞完整检查。
- 主世界56/56群系和地表材料规则完整检查。
- 水岸审计及水源所有权大量列扫描（基准302848列）关键异常全为0。
- 构建并部署命令为 `cd java/neoforge-mod && build.cmd`；只有看到 `BUILD SUCCESSFUL` 和HMCL MOD目标路径才称为已部署。
- 新模型引擎缓存键 `v15 -> v16`；已有 GeoWorld 存档自带模型/已生成区块不会自动刷新，测试矿脉和河口必须在**新存档**或确实没有生成过的区块验收。禁止为了验证修改用户存档。
- 涉及更多矿体几何输出量，需要继续观察真实HMCL区块性能日志，不凭仅有的单次合成基准就断言加载性能改善。
