## 验收边界

本次不是复用旧世界，更不是改 `level.dat` 制造出生点。对于每次测试，**在执行 Minecraft 服务端前，检查对应的新世界目录不存在**。服务端自行创建 `level.dat`、GeoWorld 绑定文件、持久化 `world.geoworld` 和原生 Anvil 区块，随后通过 RCON `save-all flush`、`stop` 正常保存退出。

两个全新世界均在一个独立 ADM 工作树中的本地环回端口进行。没有修改此前的 R8.1e 正式实验世界、旧存档、Go 模型生成算法或出生点候选排序。

## 真实游戏中的出生点修复

两个 `level.dat` 都在**原生服务器写入并保存之后**进行只读检查。使用 `scripts/verify_geoworld_voxel_world.py` 进行种子、生成器与 GeoWorld 绑定前置校验，均全部通过。

随后使用只读 Anvil 解码工具检查确切 SpawnX/Z：

- `(1088,448)`：`minecraft:full`，天然地面 Y106，保存 SpawnY107。
- `(192,192)`：`minecraft:full`，天然地面 Y103，保存 SpawnY104。

独立的 `GeoWorldSpawnHeightVerifier` 读取两份实际保存模型，两个种子也均复算出完全相同的 X/Y/Z，说明服务端出生点坐标和 Java Runtime 模型高度映射一致。

**结论：R8.1f 的出生点 Y=-64 修复现在通过了两个真正空目录新世界的首次创建、原生保存和实际方块复验；不再局限于旧存档的回放测试。**

## 性能问题现状

此前 `123456` 首次启动有一次 **535 秒**异常。对单个 `GeoWorldSpawnPlanner.find` 的独立直接性能采样，两个出生点倾向权重分别约为 **1.24 秒 / 0.81 秒**；不能由此解释此前几百秒的初始化开销。

本次受控实测：

- 相同种子、有缓存创建全新世界：16.678 秒。
- 不同种子、完全无对应模型缓存创建全新世界：45.427 秒。
- 此前 535 秒异常：**本轮未复现**。

这不是“535 秒问题已修复”；其根因尚无确定证据。之前运行时同机存在较高的 CPU/内存压力，可能对性能产生影响，但本次未完成对照实验，不能定性为唯一原因。未来发现可重复的慢启动再进行定点 profiling，**不应无依据改出生点规划/世界模型生成算法**。
